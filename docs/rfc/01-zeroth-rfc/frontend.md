# Frontend

## 1. Область и требования

Файл про graph-frontapp и graph-admin-frontapp: стек, экраны, как ходим в бэкенд. Общая схема в [README](README.md), бэкенд в [backend.md](backend.md). Номера Ф, БР, Я, Д - из RFC-001.

Что важно для фронта:

- Фронт ничего не считает. Риск, признаки, ключевой путь и доступные действия приходят из API.
- Логина нет, автор записей всегда «аналитик» (Ф1, Д-1).
- Время везде в UTC и с подписью (Д-4).
- Новые группы забираем polling'ом.
- Граф должен читаться на 30 счетах без автосворачивания (БР-8).
- PDF из карточки совпадает с экраном по данным: те же счета, числа, путь, причины (БР-9).

Только десктоп от 1280 px, только русский, без i18n.

## 2. Предлагаемое решение

### Стек

| Что                    | Предлагаем                         | Кратко почему                                         |
|------------------------|------------------------------------|-------------------------------------------------------|
| Язык и сборка          | TypeScript + Vite                  | обычная SPA, SSR не нужен                             |
| UI                     | React                              |                                                       |
| Роутинг                | React Router                       | экранов мало, фильтры держим в query-параметрах       |
| Запросы и polling      | TanStack Query                     | `refetchInterval` и кэш из коробки                    |
| Клиент API             | openapi-typescript + openapi-fetch | типы из Swagger Huma, руками не пишем                 |
| UI-kit                 | Mantine                            | таблицы, мультиселект, таймлайн, модалки уже есть     |
| Граф                   | Cytoscape.js                       | подсветка по классам, zoom, поиск узла, раскладки     |
| PDF                    | @react-pdf/renderer                | собираем из тех же данных, что и карточка             |
| Время                  | dayjs (utc)                        |                                                       |
| Тесты                  | Vitest, MSW, Playwright            | MSW чтобы не ждать бэкенд, Playwright для демо-сценария |
| Линтер                 | ESLint + Prettier                  |                                                       |
| Пакеты                 | pnpm workspaces                    |                                                       |

### graph-frontapp

Один экран: слева список групп, справа картина и карточка выбранной. Выбор группы открывает обе сразу (БР-4).

- Список: поля из БР-2, фильтры по статусу, типу и риску (риск - мультивыбор), сортировка по риску или времени. Выбранная группа и фильтры лежат в URL, перезагрузка ничего не сбрасывает.
- Polling списка раз в пару секунд, пока вкладка активна. Новая группа идёт первой с меткой и подсветкой до первого открытия (БР-4). Флаг «открыта» лучше хранить на бэкенде, иначе подсветка зависит от браузера.
- Картина: Cytoscape. Ключевой путь и первые 3 общие точки подсвечены, остальное приглушено. Клик по счёту подсвечивает связи, сверху поиск счёта, zoom колёсиком. Ключевой путь, порядок общих точек и «ещё N путей» считает бэкенд, фронт только рисует. Раскладка зависит от типа: цепочка слева направо (dagre), кольцо по кругу, устройство и адрес звездой. Случайную инициализацию отключаем, чтобы группа всегда выглядела одинаково.
- Карточка: риск, объяснение, путь словами, ключевые счета и события, история решений. Отдельно список сырых событий, там же признаки операции (Ф10).
- Решения: кнопки рисуем по `allowed_actions` из API, автомат статусов на фронте не дублируем. Подтверждение, отклонение и откат идут через модалку с обязательным комментарием.
- PDF: на клиенте, снимок картины растром из `cy.png()`. Для кириллицы нужно подключить свой шрифт. Только ключевой состав карточки, без сырых событий.
- Ошибки API показываем текстом причины, не кодом.

### graph-admin-frontapp

Боковое меню, экраны:

- Генерация (Ф8): выбор схем, seed, режим отправки (пачкой или потоком).
- Поток и журнал (Ф7): выбор сценария, старт и стоп, «отправить то же событие ещё раз», журнал с дублями и битыми записями.
- Повтор отрезка (Ф9): период, запуск, совпало или список расхождений.
- Сверка с разметкой (Ф11): таблица по типам схем.
- Загрузка CSV из AML-Data (см. [backend.md](backend.md)).

Инструкцию по загрузке CSV показываем блоком над формой на экране загрузки. Текст лежит в отдельном md-файле рядом с экраном, чтобы править без React. Что в нём будет (откуда брать файл, какой, ограничения), допишем, когда бэкенд определится с форматом.

Список групп и картину в админке не дублируем, там только ссылка в graph-frontapp.

### Структура в репозитории

```
frontend/
  graph-frontapp/
    src/{api, features, shared}
  graph-admin-frontapp/
    src/{api, features, shared}
```

Внутри `features` делим по фичам из ТЗ (groups-list, group-graph, group-card, group-decision), так проще сверяться с RFC-001. Общий пакет в `frontend/packages/` заведём, когда начнёт дублироваться код.

Клиент генерируем командой `pnpm gen:api` из Swagger Huma. Откуда брать спеку и как проверять в CI, что клиент свежий, решаем вместе с [ci.md](ci.md).

## 3. Рассмотренные альтернативы

- Next.js и другой SSR: не нужен, SEO нет, лишний сервер в деплое.
- Vue, Svelte: подошли бы, взяли React из-за экосистемы. Cytoscape от фреймворка не зависит, так что замена дёшево.
- Граф:
  - React Flow - больше про редакторы схем, подсветку и раскладки пришлось бы дописывать;
  - Sigma.js - под тысячи узлов, у нас до 30, подписи на рёбрах слабее;
  - D3 руками - слишком много работы для спринта.
- UI-kit: shadcn/ui + Tailwind (таблицы и мультиселекты собирать самим), Ant Design, MUI.
- Состояние: Redux Toolkit или SWR. У TanStack Query меньше кода под polling, а клиентского состояния почти нет.
- SSE или WebSocket вместо polling: в README уже выбран polling, вернёмся при росте нагрузки.
- orval вместо openapi-fetch: генерирует хуки, но кода больше и отлаживать сложнее.
- PDF:
  - `window.print()` зависит от браузера и диалога печати;
  - html2canvas + jsPDF превращает всё в картинку;
  - генерация на бэкенде - рендерер ради одного экрана, не для MVP.

## 4. Риски и компромиссы

1. **Граф нечитаем на 30 счетах.** Главный риск. Заранее собрать прототип на данных генератора с 30 счетами и показать команде до вёрстки остального.
2. **Контракт с бэкендом.** Фронту нужны от API ключевой путь, порядок общих точек, `allowed_actions`, флаг «открыта». Пока их нет, сидим на моках (MSW).
3. **PDF.** Кириллица и растровый снимок, который теряет резкость при печати. Для MVP нормально, вектор можно сделать позже через экспорт SVG.
4. **Polling.** Новая группа появляется с задержкой до интервала, список перезапрашивается целиком. На нескольких тысячах событий терпимо.
5. **Две аппки.** Для демо переключаемся между вкладками, часть кода может задвоиться.

## 5. Открытые вопросы

- Где запуск потока и журнал? В Ф1 аналитик видит «запустить поток» на своём экране, а по README генератор в admin-api. Либо только в админке со ссылкой, либо мини-панель в graph-frontapp, которая ходит в admin-api.
- Нужна ли загрузка CSV? В [backend.md](backend.md) она есть, а БР-11 говорит «загрузки файла для демо нет».
- Что показывать в списке по умолчанию? Я-8 в RFC-001 обрывается на полуслове, а БР-5 на неё ссылается.
- Что в первом спринте? Метка [Спринт 1] только у Ф1, Ф2, Ф7, Ф8, Ф10, а картина (Ф4) и карточка (Ф5) без метки, хотя без них демо не получится.
- Контракт API: поля из риска 2, нужна ли пагинация списка, где лежит спека OpenAPI.
- PDF: растр или вектор, и шаблон отчёта (RFC-001 оставляет на проектирование карточки).
