# Frontend

## 1. Область и требования

Файл про graph-frontapp и graph-admin-frontapp: стек, экраны, как ходим в бэкенд. Общая схема в [README](README.md), бэкенд в [backend.md](backend.md), продуктовые требования в [features.md](../../features.md).

Что важно для фронта:

- Фронт ничего не считает. Риск, признаки, ключевой путь и доступные действия приходят из API.
- Авторизация и автор записей: вопрос открыт, см. [§5](#5-открытые-вопросы) и [backend.md](backend.md).
- Время везде в UTC с указанием часового пояса.
- Новые группы забираем polling'ом.
- Граф должен читаться на 30 счетах без автосворачивания (Ф4).
- PDF из карточки совпадает с экраном по данным: те же счета, числа, путь, причины (Ф5).

Только десктоп от 1280 px, только русский, без i18n.

## 2. Предлагаемое решение

### Стек

| Что                    | Предлагаем                         | Кратко почему                                         |
|------------------------|------------------------------------|-------------------------------------------------------|
| Язык и сборка          | TypeScript + Vite                  | обычная SPA, SSR не нужен                             |
| UI                     | React                              |                                                       |
| Роутинг                | React Router                       | экранов мало, фильтры держим в query-параметрах       |
| Запросы и polling      | TanStack Query                     | `refetchInterval` и кэш из коробки                    |
| Клиент API             | openapi-typescript + openapi-fetch | типы из Swagger Huma, руками не пишем                 |
| UI-kit                 | Mantine                            | таблицы, мультиселект, таймлайн, модалки уже есть     |
| Граф                   | Cytoscape.js (+ cytoscape-dagre, cytoscape-svg) | подсветка по классам, zoom, раскладки цепочек (dagre), векторный экспорт в SVG |
| PDF                    | @react-pdf/renderer                | собираем из тех же данных, что и карточка             |
| Время                  | dayjs (utc)                        |                                                       |
| Тесты                  | Vitest, MSW, Playwright            | MSW для тестов компонентов, Playwright для демо-сценария |
| Линтер                 | ESLint + Prettier                  |                                                       |
| Пакеты                 | pnpm workspaces                    |                                                       |

### graph-frontapp

Один экран: слева список групп, справа картина и карточка выбранной. Выбор группы открывает обе сразу (Ф2, Ф4, Ф5).

Описание ниже словами, и по нему трудно представить интерфейс. Макет (Figma или кодовый прототип) нужен, но это уже после RFC. В RFC его не делаем.

- Список: поля из Ф2 (тип, уровень риска, число счетов, общая сумма, время последнего события, статус), фильтры и сортировка из Ф3 (фильтры по статусу, схеме и риску с мультивыбором, сортировка по риску или времени). Выбранная группа и фильтры лежат в URL, перезагрузка ничего не сбрасывает.
- Polling списка раз в пару секунд, пока вкладка активна. Новая группа идёт первой с меткой и подсветкой до первого открытия (Ф2).
- Картина (Ф4): Cytoscape. Ключевой путь и первые 3 общие точки подсвечены, остальное приглушено. Клик по счёту подсвечивает связи, сверху поиск счёта, zoom колёсиком. Ключевой путь, порядок общих точек и «ещё N путей» считает бэкенд, фронт только рисует. Раскладка зависит от типа: цепочка слева направо (dagre), кольцо по кругу, ферма и адрес звездой. Случайную инициализацию отключаем, чтобы группа всегда выглядела одинаково.
- Карточка (Ф5): риск, объяснение, путь словами, ключевые счета и события, история решений. Отдельно список сырых событий, там же признаки операции (Ф11).
- Решения (Ф6): кнопки рисуем по `allowed_actions` из API, автомат статусов на фронте не дублируем. Подтверждение, отклонение и откат идут через модалку с обязательным комментарием.
- PDF (Ф5): на клиенте, векторный экспорт картины в SVG (cytoscape-svg). Для кириллицы нужно подключить свой шрифт. Только ключевой состав карточки, без сырых событий.
- Ошибки API показываем текстом причины, не кодом.

### graph-admin-frontapp

Боковое меню, экраны:

- Генерация (Ф8): выбор схем, seed, режим отправки (пачкой или потоком).
- Поток и журнал (Ф7): выбор сценария, старт и стоп, «отправить то же событие ещё раз», журнал с дублями и битыми записями.
- Повтор отрезка (Ф9): период, запуск, совпало или список расхождений.
- Сверка с разметкой (Ф10): таблица по типам схем.
- Очистка БД (Ф13): очистка данных за период для перезапуска демо и проверки сценариев заново.
- Данные из AML-Data (CSV): как именно они попадают в систему, решаем вместе с бэкендом, см. [§5](#5-открытые-вопросы). Предпочтительный вариант: предзагруженные CSV лежат на бэкенде, на экране только выбор файла и запуск.

Если загрузка файла с фронта всё же понадобится, инструкцию показываем блоком над формой. Текст лежит в отдельном md-файле рядом с экраном, чтобы править без React. Что в нём будет (откуда брать файл, какой, ограничения), допишем, когда бэкенд определится с форматом.

Список групп и картину в админке не дублируем, там только ссылка в graph-frontapp.

### Структура в репозитории

```
frontend/
  graph-frontapp/
    src/{api, features, shared}
  graph-admin-frontapp/
    src/{api, features, shared}
```

Внутри `features` делим по фичам из `features.md` (groups-list, group-graph, group-card, group-decision). Общий пакет в `frontend/packages/` заведём, когда начнёт дублироваться код.

Клиент генерируем командой `pnpm gen:api` из Swagger Huma. Откуда брать спеку и как проверять в CI, что клиент свежий, решаем вместе с [ci.md](ci.md).

### Порядок работы с бэкендом

Работаем по фичам, а не от заранее описанного API. Сначала бэкенд делает фичу, ближе к концу спринта фронт подключается и делает её параллельно. Весь API целиком заранее не описываем и не мокаем: у команды мало опыта в этой области, и фронт с бэкендом разъедутся (так было в ShuKnow).

## 3. Рассмотренные альтернативы

- Next.js и другой SSR: не нужен, SEO нет, лишний сервер в деплое.
- Vue, Svelte: подошли бы, взяли React из-за экосистемы. Cytoscape от фреймворка не зависит, так что замена дёшево.
- Граф:
  - React Flow - больше про редакторы схем, подсветку и раскладки пришлось бы дописывать;
  - Sigma.js - под тысячи узлов, у нас до 30, подписи на рёбрах слабее;
  - D3 руками - слишком много работы для спринта.
- UI-kit: shadcn/ui + Tailwind (таблицы и мультиселекты собирать самим), Ant Design, MUI.
- Состояние: Redux Toolkit или SWR. У TanStack Query меньше кода под polling, а клиентского состояния почти нет.
- SSE или WebSocket вместо polling: в README уже выбран polling, вернёмся при росте нагрузки.
- orval вместо openapi-fetch: генерирует хуки, но кода больше и отлаживать сложнее.
- PDF:
  - `window.print()` зависит от браузера и диалога печати;
  - html2canvas + jsPDF превращает всё в картинку;
  - генерация на бэкенде - рендерер ради одного экрана, не для MVP.

## 4. Риски и компромиссы

1. **Граф нечитаем на 30 счетах.** Главный риск. Заранее собрать прототип на данных генератора с 30 счетами и показать команде до вёрстки остального.
2. **Контракт с бэкендом.** Фронту нужны от API ключевой путь, порядок общих точек, `allowed_actions`. Не фиксируем и не мокаем весь API заранее, иначе фронт и бэкенд разъедутся. Идём по фичам: бэкенд первым, фронт параллельно ближе к концу спринта (см. «Порядок работы с бэкендом»). У нас два фуллстека, так что это реально.
3. **PDF.** Кириллица и подключение шрифтов в @react-pdf/renderer. Векторный экспорт картины через cytoscape-svg решает проблему резкости при печати.
4. **Polling.** Новая группа появляется с задержкой до интервала, список перезапрашивается целиком. На нескольких тысячах событий терпимо.
5. **Две аппки.** Для демо переключаемся между вкладками, часть кода может задвоиться.
6. **Интерфейс непонятен по тексту.** Пока нет макета, у команды разные представления о том, что получится. Макет или прототип делаем на этапе проектирования интерфейса.

- Нужна ли авторизация и разделение пользователей для демо? (сейчас считаем, что логина нет и автор всегда «аналитик», админка и рабочее место разведены по двум вкладкам браузера; подробнее в [backend.md](backend.md))
- Как именно данные из AML-Data загружаются в систему: выбор готового файла на сервере или загрузка CSV с клиента через форму? (в [backend.md](backend.md) есть загрузка файла, на фронтенде предпочтителен выбор предзагруженного на бэкенде)
