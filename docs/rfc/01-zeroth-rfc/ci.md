# CI и деплой

## 1. Область и требования

Файл описывает локальный запуск, проверки, сборку и деплой. Инструкции: [ВМ](../../../infra/vm/README.md) и [деплой](../../../infra/deploy/README.md).

Требования:

- разворачиваемся в Яндекс Облаке за счёт гранта, ресурсы включены только тогда, когда нужны;
- деплой по кнопке, без ручных заходов на ВМ;
- деплоим с первого спринта, чтобы проблемы всплывали посреди семестра, а не в конце;
- CI/CD "в одну кнопку" не цель: делаем базово и улучшаем по ходу семестра.

## 2. Предлагаемое решение

### Площадки

Одна прерываемая ВМ в Яндекс Облаке с k3s (лёгкий Kubernetes). Каждая площадка - отдельный namespace со своим комплектом: четыре сервиса и свой Postgres.

| Площадка        | Для чего                                                                                                   |
|-----------------|------------------------------------------------------------------------------------------------------------|
| prod            | демо и проверка изменений перед мержем                                                                     |
| `stage-<ветка>` | площадка под ветку, например `stage-gsd-42`: создаётся при первом деплое, удаляется кнопкой `stage-delete` |

У stage-площадки своя чистая база, поэтому экспериментальные миграции не мешают другим веткам. Число площадок ограничено: при превышении деплой падает и показывает список существующих.

- **Адреса**: prod на `shugraph.feytox.ru`, stage на `<ветка>.shugraph.feytox.ru`, например `gsd-42.shugraph.feytox.ru`. Домен на Cloudflare (только DNS), две A-записи: `shugraph` и wildcard `*.shugraph`. IP ВМ меняется при каждом запуске, поэтому при включении обновляем обе.
- **HTTPS**: на первом спринте только HTTP. Потом cert-manager с wildcard-сертификатом от Let's Encrypt через DNS-01 в Cloudflare.
- **Фронты**: статика в nginx внутри кластера, на одном хосте с API, поэтому CORS не нужен. Позже prod-фронт, возможно, перенесём в Object Storage.
- **Postgres**: StatefulSet в каждом namespace, внутри по базе на сервис (см. [backend.md](backend.md)). Данные лежат на диске ВМ и переживают выключение.

### Включение и выключение

- Кнопки `up` и `down` в GitHub Actions. `up` запускает ВМ, ждёт кластер и обновляет DNS.
- Через час после последнего `up` или деплоя ВМ выключает workflow `autodown`. Чтобы ВМ поработала дольше, его запуск отменяют.
- Каждую ночь в 01:00 по МСК `down` выключает ВМ по расписанию, даже если `autodown` отменили.

### Проверки

- На каждый PR GitHub Actions гоняет линтеры, юнит-тесты и проверку, что сгенерированные API-клиенты совпадают со Swagger-спекой. Только для изменённых сервисов. Для публичного репозитория это бесплатно, лимиты не тратятся (грант тем более).
- e2e-тесты на Playwright против stage-площадки запускаются отдельной кнопкой.

### Деплой

Используем модель **deploy-to-merge**: сначала выкатываем ветку на prod, проверяем и только потом мержим.

1. По желанию выкатываем ветку на её stage-площадку и проверяем там.
2. Подтягиваем в ветку свежий main, пишем в чат команды, что выкатываемся на prod, и выкатываем.
3. Если всё в порядке, мержим PR отдельной кнопкой и удаляем stage-площадку ветки. Если нет, выкатываем на prod обратно main. Откат кода схему не откатывает: после ломающей миграции main может не заработать на новой схеме.

Без деплоя PR не смержить: ruleset требует статус `deploy/prod`. Если PR меняет сервисы, `infra/` или деплой, `checks` ставит ему pending, а success ставит деплой на prod всех сервисов сразу. PR, где поменялись только документация и проверки, получает success без деплоя. Ветку, отстающую от main, на prod выкатить нельзя, а мержить ruleset разрешает только ветку с последним main. Поэтому после чужого мержа ветку с кодом выкатывают заново.

Кнопка деплоя принимает ветку, площадку (prod или stage) и сервисы: можно выкатить любой из четырёх или все сразу. На новую stage-площадку выкатываются все сервисы. Её имя берётся из ветки, поэтому фронт и бэк из разных веток на ней не смешиваем: нужную комбинацию сливаем в одну ветку. Дальше по шагам:

1. прогоняем проверки, если у коммита ещё нет успешных, например в PR они не успели закончиться;
2. собираем образ и пушим в Yandex Container Registry с тегом коммита;
3. запускаем миграции goose отдельным Job'ом с тем же образом;
4. если миграции прошли, обновляем Deployment.

### Секреты и конфиг

- **GitHub Secrets**: доступы CI (ключ сервисного аккаунта YC, SSH-ключ, токен Cloudflare).
- **k8s Secrets**: пароли Postgres и прочие секреты приложений. Генерируются один раз при создании площадки и живут только в кластере.
- Остальной конфиг передаём переменными окружения в манифестах.

### Локальный запуск

- docker compose поднимает Postgres и сервисы. Сервис, над которым работаешь, можно запускать из IDE.
- make для локальных задач: поднять окружение, линтеры, тесты, генерация клиентов. Всё, что трогает облако, живёт только в GitHub Actions, поэтому доступы к облаку нужны CI, а не каждому разработчику.

## 3. Рассмотренные альтернативы

- **Managed Kubernetes**: мастер тарифицируется отдельно и съедает грант.
- **Serverless (Cloud Functions, Serverless Containers)**: архитектура проекта должна быть под serverless, а опыта в этом у нас нет.
- **ВМ + docker compose**: пробовали, слишком много ручных действий: зайти на ВМ, подтянуть изменения, перезапустить compose.
- **Managed PostgreSQL**: работает и тарифицируется отдельно от ВМ.
- **Фронт в Object Storage**: отдельный способ деплоя, плюс CORS или проксирование API. Вернёмся к нему для prod позже.
- **Cloudflare proxy для HTTPS**: в России работает нестабильно (спасибо, РКН).
- **Автовыключение через Cloud Function**: лишний компонент, расписание в GitHub Actions проще.
- **Таймер через cron**: GitHub запускает расписание с опозданием до получаса, а отложенного запуска workflow у него нет, поэтому `autodown` просто ждёт час в отдельном job'е.
- **Merge-to-deploy**: мерж в main сам выкатывается на prod. Сломанное изменение при этом уже в main, и пока не сделали revert или hotfix, main нерабочий. В deploy-to-merge в main попадает только то, что уже проверено на prod.
- **Фиксированные слоты stage-1 и stage-2**: слоты приходится делить в чате, а в базе остаются данные и миграции прошлой ветки.
- **Argo CD с генератором по PR**: сам создаёт и удаляет площадки, но это ещё один постоянный сервис на маленькой ВМ.
- **Не делать CI на первых спринтах**: ловушка. Потом не будет времени на "бесполезную инфру", а подводные камни всплывут в конце семестра.

## 4. Риски и компромиссы

1. **Бюджет утечёт на неделях защит.** Там решение должно работать не час, а несколько недель подряд. Пока не считаем, но держим в голове.
2. **Прерываемая ВМ гаснет сама** минимум раз в сутки, иногда прямо во время работы. Для разработки терпимо, достаточно нажать `up`.
3. **Всё на одной ВМ.** Тяжёлая stage-площадка может отнять ресурсы у prod. Для учебного проекта приемлемо.
4. **Двое выкатятся на prod одновременно** и затрут друг другу изменения. Договариваемся в чате, автоматическую блокировку не делаем.
5. **Забытые stage-площадки** занимают память и диск ВМ. Ограничиваем их число, удаляем кнопкой `stage-delete`.
6. **Старые DNS-записи в кэше.** IP ВМ меняется при каждом запуске, а резолверы и браузеры какое-то время помнят старый адрес, и площадка открывается не сразу. Снижаем коротким TTL у A-записей.

## 5. Открытые вопросы

- Размер ВМ: хватит ли 2 vCPU и 4 ГБ на prod и несколько stage-площадок, или сразу брать больше? Сколько stage-площадок разрешаем одновременно? Выясним на практике.
- Как живём на неделях защит: переходим на непрерываемую ВМ? Сколько это стоит?
- Тестовые данные для e2e на stage-площадке: откуда берём данные для чистой базы? Связано с вопросом про авторизацию в [backend.md](backend.md).
