# Backend

## 1. Область и требования

Файл описывает graph-api и graph-admin-api: стек, внутреннее устройство и хранение данных. Общая схема системы есть в [README](README.md).

Ключевое требование на первый спринт - **детерминированность**: один и тот же вход всегда даёт один и тот же результат. Отсюда два правила:

1. все вычисления опираются на время события, а не на время сервера;
2. генератор и всё, где есть случайность, запускается с фиксированным seed.

Дальше по ТЗ на бэкенде лежат:

- приём событий с защитой от повторной записи: повторная доставка не создаёт вторую операцию;
- повторное проигрывание выбранного временного отрезка;
- восстановление после сбоя без потери и удвоения операций.

Объём: несколько тысяч событий система должна переваривать спокойно. Точных требований нет, см. открытые вопросы.

## 2. Предлагаемое решение

### Стек

| Что                           | Предлагаем                           | Кратко почему                                                         |
|-------------------------------|--------------------------------------|-----------------------------------------------------------------------|
| Роутер                        | chi                                  | легковесный, совместим с `net/http` и стандартным `context`           |
| Эндпоинты и Swagger           | Huma v2 + humachi                    | code-first: спека генерируется из кода. Spec-first пробовали, оверхед |
| Драйвер Postgres              | pgx v5                               |                                                                       |
| Запросы                       | sqlc                                 | пишем обычный SQL, получаем типизированный Go-код                     |
| Миграции                      | goose                                | вшиты в бинарник, будем запускать отдельной командой                  |
| Конфиг                        | caarlos0/env                         | конфиг из переменных окружения, будет удобно в k8s                    |
| Логи                          | log/slog                             |                                                                       |
| Клиент admin-api -> graph-api | oapi-codegen                         | генерируем по Swagger graph-api, а не пишем руками                    |
| Тесты                         | testing + testify, testcontainers-go | тесты на настоящем Postgres в контейнере                              |
| Фейковые данные               | gofakeit                             | догенерировать то, чего нет в датасете: устройства, IP, входы         |
| Линтер                        | golangci-lint                        |                                                                       |

### graph-api

- Чистая архитектура с явными слоями: транспорт (HTTP, Huma) -> бизнес-логика -> репозитории (sqlc). Структура пакетов по принятым в Go практикам (`cmd/`, `internal/`).
- События приходят через HTTP ingest. Каждое проверяется и записывается идемпотентно.
- Источник правды для графа - Postgres. Для вычислений нужный подграф поднимаем из базы по запросу. Так реплики graph-api остаются без состояния и масштабируются без рассинхрона.
- Поиск групп и оценка риска пока не проработаны, ждём определений из [business.md](business.md).
- Фронтенд ходит в API по REST, новые находки забирает polling'ом.

### graph-admin-api

- Первый источник данных - CSV из [AML-Data](https://github.com/IBM/AML-Data/). Файл загружается через админку, мы парсим его и маппим поля в нашу модель событий. Инструкция для пользователя админки описана в [frontend.md](frontend.md).
- В AML-Data только переводы, устройств, IP и событий входа там нет. Их догенерируем через gofakeit.
- Два режима отправки в graph-api:
  - **пачками** - залить историю разом;
  - **поток** - события идут по одному с задержкой, имитируя живое время. Нужен для демо, где группа должна появиться прямо во время потока. На первом спринте можно обойтись без него и начать с пачек.
- Храним свою разметку (какие операции входят в мошеннические схемы), чтобы потом проверять качество поиска (тоже не на первом спринте, но было бы круто сделать).
- Позже, возможно, подключим другие генераторы (например, AMLSim) и свой.

### Хранение

Один инстанс Postgres, у каждого сервиса своя база и свои миграции. В чужие базы сервисы не ходят, общаются только через API.

### Структура в репозитории

`backend/graph-api` и `backend/graph-admin-api`. Как раскладывать `go.mod`, пока не решили.

## 3. Рассмотренные альтернативы

### Стек

| Что                           | Альтернатива                           | Почему нет                                                                                                  |
|-------------------------------|----------------------------------------|-------------------------------------------------------------------------------------------------------------|
| Роутер                        | stdlib `http.ServeMux`                 | нет middleware из коробки и regex валидации параметров, громоздкая модульность роутеров                     |
|                               | gin                                    | использует свой context, много транзитивных зависимостей                                                    |
|                               | gorilla/mux                            | legacy                                                                                                      |
| Эндпоинты и Swagger           | swaggo/swag (Swagger из комментариев)  | нет автоматической валидации, надо документировать код                                                      |
|                               | ogen, oapi-codegen (spec-first подход) | автогенерация громоздкого кода, интеграция с chi сложнее, оверхэд для маленькой команды                     |
| Драйвер Postgres              | `database/sql` + lib/pq                | сами авторы lib/pq рекомендуют pgx, проект не развивается                                                   |
| Запросы                       | GORM, ent, bun (ORM)                   | запросы, написанные code-first, сложнее читаются и поддерживаются. Не все запросы можно написать через ORM. |
|                               | squirrel (сборщик запросов)            | для простых запросов это оверхэд. Можно использовать для динамики.                                          |
| Миграции                      | golang-migrate                         | по два файла на миграцию, неудобно делать из кода, ручной откат при невалидной транзакции.                  |
|                               | atlas                                  | нельзя делать из кода, высокий порог входа.                                                                 |
| Конфиг                        | kelseyhightower/envconfig              | устарел                                                                                                     |
|                               | cleanenv                               | нет слияния нескольких файлов конфига                                                                       |
|                               | viper                                  | тяжелый                                                                                                     |
| Логи                          | zap, zerolog                           | призваны оптимизировать стандартную библиотеку при высокой нагрузке                                         |
| Клиент admin-api -> graph-api | ручной клиент на `net/http`            | рутина, нет валидации на этапе компиляции                                                                   |

### Брокер сообщений вместо HTTP ingest

Kafka, NATS или Redis Streams между генератором и graph-api. Даёт буфер под нагрузку и повторное проигрывание из коробки. От идеи не отказываемся, но для старта это лишняя инфраструктура, HTTP проще. Вернёмся к брокеру, когда упрёмся в нагрузку. Схема в README при этом не меняется.

### Монолит

Стартовать проще, но генератор и ядро масштабировались бы только вместе, а ядро зависело бы от генератора.

### Графовая БД

Для старта берём знакомый Postgres, графовую БД хотим попробовать позже.

### Граф целиком в памяти

Быстрые обходы, но у каждой реплики будет своя копия графа, и они разъедутся. Пока отложили.

## 4. Риски и компромиссы

1. **Генератора не хватит для антифрод-сценариев.** Самый вероятный риск. В AML-Data только переводы, устройства и входы придётся догенерировать, и не факт, что получатся правдоподобные схемы мошенничества.
2. **Не получится адекватный алгоритм.** Опыта в антифроде у команды нет. Снижаем риск через [business.md](business.md), консультацию специалиста через эксперта и старт с простых правил.
3. **Postgres - не графовая БД.** Обходы графа на SQL могут быть громоздкими и медленными. Для MVP это приемлемо.
4. **Не вывезем большой объём.** HTTP ingest и выборка подграфа из Postgres могут не справиться с большим потоком. Для MVP это приемлемо.

- Какой объём показывать на демо: сколько событий и с какой скоростью? (скорее всего, решаем сами)
- Как устроены поиск групп и оценка риска? Зависит от [business.md](business.md).
- `go.mod`: один общий в `backend/` или свой у каждого сервиса?
- Авторизация:
  - нужна ли она вообще;
  - если нужна, раздельные ли учётки у админки и основного сервиса;
  - если нужна, разделены ли данные между учётками, или всё общее и авторизация только закрывает доступ посторонним;
  - если не нужна, то как будем без отдельной тестовой УЗ разделять данные для API и Playwright staging тестов?
