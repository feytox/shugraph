# Бизнес-логика и фичи первого спринта

---

## 1. Область и требования

Файл покрывает продуктовую часть первого спринта: пользовательские сценарии и состав фич. Мошеннические сценарии и ядро обнаружения (Я-1–Я-9) вынесены в [schemes.md](../schemes.md).

Требования из ТЗ и договорённостей, к которым он относится:

- поток операций и событий входа, постепенное обновление без пересборки;
- поиск общих устройств, сетевых адресов, быстрых цепочек и замкнутых переводов;
- рабочее место аналитика: список подозрительных групп, карточка расследования, картина связей;
- генератор обычного поведения и размеченных схем для повторяемой проверки;
- расчёт признаков операций и групп, объяснение через путь связей;
- подтверждение или отклонение находки аналитиком;
- повторная доставка не создаёт вторую операцию; повторный прогон даёт тот же результат;
- на показе: новая группа выделяется в потоке, виден подграф и причины, дубли игнорируются, повтор детерминирован.

### Допущения
**Д-1. Один аналитик.** Отдельного логина нет. Автор любой записи в истории — всегда «аналитик» по умолчанию. Это допущение MVP, а не бизнес-правило: ролей, имён и прав пока нет.
**Д-2. Числа зафиксированы здесь.** Окно 24 часа и пороги из ядра обнаружения — принятые значения для демо. Меняются только новым решением по RFC. Настраиваемых величин в MVP нет.
**Д-3. Вне области.** Захват аккаунтов, веерная рассылка как отдельный тип (один → многим → одному без других признаков), социнженерия, блокировки операций, интеграция с банком, юридическая квалификация.
**Д-4. Время — UTC везде.** «Ночь 00:00–06:00» и «окно 24 часа» считаются по UTC для всех счетов и событий.

### Спринты
В первый спринт входят только фичи с пометкой [Спринт 1]: Ф1, Ф2, Ф7, Ф8, Ф10. Остальное — Ф3–Ф6, Ф9, Ф11 — вынесено в [backlog.md](../backlog.md). Бизнес-правила по всем фичам (БР-1–БР-18) — в [feature-rules.md](../feature-rules.md). Схемы и ядро обнаружения (Я-1–Я-9) — в [schemes.md](../schemes.md).

## 2. Предлагаемое решение

### 2.1. Мошеннические сценарии — см. [schemes.md](../schemes.md)

4 схемы (общие устройства, общие адреса, быстрые цепочки, кольца) с легендами, примерами и правовой проекцией без изменений вынесены в `schemes.md`.

### 2.2. Ядро обнаружения — см. [schemes.md](../schemes.md)

Когда счета становятся группой и как считается риск (Я-1–Я-9: окно 24 часа, пороги устройства/адреса/цепочки/кольца, расчёт риска, жизненный цикл). Это ядро, а не отдельные фичи; все пороги зафиксированы в Д-2 и меняются только решением по RFC. Тексты без изменений вынесены в `schemes.md`.

### 2.3. Пользовательские сценарии и фичи

#### Ф1. Открыть рабочее место [Спринт 1]
**Зачем:** чтобы аналитик сразу мог работать, без настройки.
**Шаги:**
1. Открыть приложение.
2. Увидеть список групп и возможность запустить поток.
**Что должно получиться:** рабочее место доступно, автор действий подписывается как аналитик для истории решений.
**Как проверить:** открыть с чистого браузера — нет просьб логина, список и запуск на месте.

#### Ф2. Список найденных групп [Спринт 1]
**Зачем:** увидеть все, что система уже нашла, и выбрать, что разбирать.
**Шаги:**
1. Открыть список.
2. Для каждой группы увидеть: тип, уровень риска, сколько счетов, какая общая сумма, когда последнее событие, статус.
3. Выбрать группу для разбора.
**Что должно получиться:** появление новой группы в потоке заметно; по умолчанию для разбора предлагается первая из списка.
**Как проверить:**
- загрузить пример с 3 группами — все 3 в списке, у каждой есть тип, риск, число счетов, сумма, время последнего события, статус;
- очистить всё — видна подсказка про запуск потока.

#### Ф3–Ф6. Вне первого спринта — см. [backlog.md](../backlog.md)

Поиск и сортировка (Ф3), картина связей (Ф4), карточка расследования (Ф5), решение и статусы (Ф6) — вне Спринта 1, тексты без изменений вынесены в бэклог.

#### Ф7. Включить поток событий [Спринт 1]
**Зачем:** смотреть, как группы появляются вживую.
**Шаги:**
1. Выбрать заготовленный сценарий и запустить демо-поток. Загрузки файла в демо нет.
2. Наблюдать, как список пополняется новыми группами.
3. Для проверки дублей — нажать «отправить то же событие ещё раз».
4. Остановить поток. Остановка группы не меняет: открытые остаются открытыми.
**Что должно получиться:** запуск и остановка — по одному действию; «за пару минут» — свойство демо-набора (сценарий построен так, чтобы группа появилась быстро), а не требование к системе.
**Как проверить:** запустить сценарий «цепочка» — группа появилась в списке с правильным типом и временем; в журнале потока видно, что события приняты (счёт растёт).

#### Ф8. Учебный генератор обычного и плохого поведения [Спринт 1]
**Зачем:** чтобы каждый раз проверять на одинаковых данных: где правда, известно заранее. В Спринте 1 осознанно: без генератора демо не проходит проверку на повторяемость, заменить его нечем.
**Шаги:**
1. Запросить генерацию: обычные клиенты (зарплата, траты) + внедрённые 4 схемы.
2. В генерации есть и переводы, и события входа (входы нужны для устройства и адреса).
3. Получить пометки: у каждого события указаны схема и группа; у каждого события есть свой номер для проверки дублей.
4. Прогнать через поток и сверить: генератор сказал «тут кольцо из 3 счетов» — система его нашла.
**Как проверить:** сгенерировать набор с по одной схеме каждого типа — все 4 нашлись и правильно названы.

#### Ф9. Вне первого спринта — см. [backlog.md](../backlog.md)

Проигрывание отрезка времени заново — вне Спринта 1, текст без изменений вынесен в бэклог.

#### Ф10. Признаки операции и группы — из чего складывается подозрение [Спринт 1]
**Зачем:** объяснить простыми словами, что значит «расчёт признаков». Это список понятных фактов, которые влияют на риск и показываются в карточке.
**Что это такое:** у каждой операции и у каждой группы есть набор признаков:
- для операции: сумма необычная для счёта (сравнение с обычной историей этого счёта из демо-набора), получатель новый (первый раз), ночь 00:00–06:00 UTC, выходной (отдельный признак времени), устройство/адрес новые для клиента, деньги ушли дальше в течение 15 минут;
- для группы: сколько счетов связано, что общего, за сколько минут, сколько хопов/кругов, сколько денег дошло.
**Шаги:**
1. Выбрать операцию — увидеть её признаки списком.
2. Выбрать группу — увидеть все её признаки.
3. Эти же признаки уезжают в карточке на проверку.
**Как проверить:** открыть группу «цепочка» — видны длина, время и сохранённая сумма, совпадают с картиной; открыть «общее устройство» — видно число клиентов и время скученности; все признаки из детального списка отражены в карточке.

#### Ф11. Вне первого спринта — см. [backlog.md](../backlog.md)

Сверка с разметкой генератора — вне Спринта 1, текст без изменений вынесен в бэклог.

### 2.4. Что показываем заказчику (первый спринт)

1. Включаем поток — в списке появляется новая группа (цепочка или кольцо).
2. Открываем её — видна причина риска.
3. Шлём то же событие повторно — второй операции нет, повтор виден в журнале потока.

Продолжение демо (повтор отрезка, карточка в PDF) — см. [backlog.md](../backlog.md).

### 2.5. Бизнес-правила по фичам — см. [feature-rules.md](../feature-rules.md)

Покрытие: у каждой фичи есть свои правила. Ядро обнаружения (Я-1–Я-9, см. [schemes.md](../schemes.md)) — не фича, работает в Ф2–Ф6 и Ф10, результат используется в Ф9 и Ф11. Полная таблица и тексты БР-1–БР-18 без изменений вынесены в [feature-rules.md](../feature-rules.md).

## 3. Рассмотренные альтернативы

Что рассматривали и почему не выбрали:

- **Веер, захват аккаунта, социнженерия как отдельные типы.** Отложены: в ТЗ заданы только 4 паттерна, остальное раздувает MVP. Веер как часть схем 1–2 учитывается (точка сбора), но сам по себе группу не создаёт.
- **Операции как узлы графа.** Не описываем в этом файле: способ отображения решится при проектировании.
- **Автосворачивание больших картин.** пусть фронтенд выбирает
- **Настраиваемые пороги.** Отклонено для MVP: числа зафиксированы в Д-2
- **Прямой переход «новая → решение».** Запрещён: решение только через «в работе», иначе теряется фиксация ответственности.
- **Фильтр «высокий и выше» одной опцией.** Выбран множественный выбор уровней: гибче и согласуется с Я-8 (см. [schemes.md](../schemes.md)).
- **Все сырые события в PDF.** Отклонено: файл раздуется; в PDF только ключевой состав.
- **Топ-3 признаков в карточке.** Отклонено: в карточке все признаки единым списком.
- **Загрузка файла в демо.** Не нужна: только заготовленные сценарии + кнопка повтора события.

## 4. Риски и компромиссы

Чем жертвуем ради сроков и что может пойти не так:

- **NAT и общие устройства.** Один адрес делят сотни честных клиентов; одно устройство — семья. Компромисс: высокий порог по адресу (4 счёта + денежные связи), пометка про провайдера, семья из 2 не срабатывает; остаточные ложные разбирает аналитик.
- **Одиночный круг без повтора группу не создаёт.** Сознательно пропускаем разовые возвраты ради меньшего числа ложных; повтор — обязательное условие кольца.
- **Низкий и средний риск по умолчанию скрыты.** Компромисс для фокуса очереди; доступны через фильтр (см. п. 1 ниже; сам Я-8 — в [schemes.md](../schemes.md)).
- **Решение окончательно по составу и риску.** Новые события после решения идут в новую группу «продолжение …»; пересмотр меняет только статус и историю.
- **Время только UTC.** Упрощает демо; для продакшена потребуются часовые пояса.
- **Шаблон подробного отчёта — отдельно.** Точные формулировки объяснений в этом файле не фиксируем.
- **Демо зависит от генератора.** Без него нет повторяемой проверки; поэтому генератор — в первом спринте.

## 5. Открытые вопросы

Что ещё не решено и требует обсуждения:

1. **Я-8 vs БР-6.** В тексте Я-8 (см. [schemes.md](../schemes.md)) сейчас: «по умолчанию в списке — все группы которые не перешли на стадию проверки». Согласовать с правилом «по умолчанию высокий и выше» (см. [feature-rules.md](../feature-rules.md), БР-6): оставить одно из двух.
2. **Спринт-маркеры — решено.** Спринт 1: Ф1, Ф2, Ф7, Ф8, Ф10. Остальное (Ф3–Ф6, Ф9, Ф11) — см. [backlog.md](../backlog.md).
3. **Вид снимка картины в PDF** (растр или вектор) — на проектирование карточки.
4. **«Модель» для сравнения** (что именно за второй вариант разбора) — определит RFC-002; в MVP сверка только для правил.
5. **Журнал событий для повтора** — подтверждение, что это просто сохранённый входящий поток за период.
