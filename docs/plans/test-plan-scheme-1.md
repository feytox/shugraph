# Тест-план: схема «ферма»

Ручной путь и негатив — на prod: http://shugraph.feytox.ru/ · Swagger: http://shugraph.feytox.ru/admin-api/docs. E2E, UI и security — на stage/PR-окружении: prod меняет данные и не подходит для автоматических прогонов.

Сценарии запускаем из Swagger graph-admin-api (`POST /admin-api/v1/scenarios/{id}/run?delay_s=0`). У сценариев фиксированные `event_id`: повторный запуск на грязной БД новых групп не создаст. Для чистого прогона нужна очистка БД (Ф13 пока не в UI).

Карточка детализирована только для фермы. В комбинированных сценариях у соседних групп проверяем только появление в списке, их карточки — вне этого плана.

Автотесты, структура и запуск — в [test/README.md](../../test/README.md).

## E2E: Playwright

Реализация и команды запуска — в [test/README.md](../../test/README.md).

Гоняем только на stage (`pr-<n>.shugraph.feytox.ru`): там своя БД на каждый PR, после закрытия окружение удаляется. Prod не трогаем, потому что решение и запуск сценария меняют данные, а очистки в UI ещё нет.

Почему Playwright: три движка в одном раннере, авто-ожидания, trace и видео при падении, `APIRequestContext` для запуска сценария и проверки API, тот же TypeScript, что у фронта. Отдельный сервис для E2E не нужен.

| ID | Что проверяем | Ожидание |
|---|---|---|
| E2E-1 | `device_farm`: запуск сценария → список → граф → карточка → подтверждение | Путь `DF-1…DF-9` проходит в Chromium без ручных действий |
| E2E-2 | `farm_and_address` и `farm_and_chain` | Ферма появляется и открывается с ожидаемыми числами `FA-1/FC-1`; вторая группа — после реализации схем 2/3 |
| E2E-3 | `without_group` | Список не меняется (`NG-1`) |
| E2E-4 | Пустой комментарий | Кнопки решения неактивны, статус группы не меняется |
| E2E-5 | Повторный запуск `device_farm` после решения | Новых групп нет, решение и риск сохраняются (`DF-11`) |

Граф — canvas: E2E проверяет, что он отрисован, видны легенда и подписи, а данные узлов и рёбер сверяем через API. Пиксельные позиции узлов в E2E не проверяем.

## UI и кросс-браузер: Playwright

Реализация и работа со скриншотами — в [test/README.md](../../test/README.md).

Проекты `chromium`, `firefox`, `webkit`; viewport `1440×900` и `1024×768`; `locale=ru-RU`, `timezoneId=UTC`, отключённые анимации, дождаться загрузки шрифта. Скриншоты сравниваем внутри одного браузера, не между браузерами; порог расхождения ~1%.

Почему так: Playwright уже нужен для E2E, визуальные снапшоты встроены (`toHaveScreenshot`), внешний сервис не требуется. Реальный Safari/iOS при необходимости отдельно проверяем через BrowserStack; для MVP трёх движков достаточно.

| ID | Что проверяем | Ожидание |
|---|---|---|
| UI-1 | Список групп | Ничего не обрезается и не наезжает: длинные суммы, даты, бейджи риска и статуса |
| UI-2 | Граф и легенда | Canvas отрисован, легенда и подписи не перекрываются, вёрстка не ломается в 3 движках |
| UI-3 | Карточка | Свёрнутое/раскрытое пояснение, таблица риска, длинный комментарий и время решения переносятся и скроллятся |
| UI-4 | Пустые и ошибочные состояния | Пустой список, ошибка списка/графа/карточки, «группа не найдена» выглядят одинаково аккуратно |
| UI-5 | Панели и узкий экран | Свёрнутые боковые панели и ширина `1024` не дают наложений и лишней горизонтальной прокрутки |
| UI-6 | Шрифты, иконки, цвета | Golos Text, иконки, цвета риска и статусов отображаются во всех трёх движках |

## Security

Что уже автоматизировано и какие сканеры запускаются отдельно — в [test/README.md](../../test/README.md).

Полный пентест в MVP не делаем: авторизации ещё нет. Проверяем поверхность, которую уже отдаём наружу. Активные сканы — только на stage; на prod допустимы пассивные проверки заголовков и TLS.

Почему эти инструменты: ZAP бесплатный и запускается в CI, умеет baseline и API-скан; Trivy проверяет CVEs в образах; `govulncheck` и `pnpm audit` уже стоят в CI и закрывают зависимости.

Активный API-скан запускаем на одноразовом stage и исключаем из обхода мутирующие админ-ручки: иначе скан сам создаст события и группы.

| ID | Что проверяем | Ожидание |
|---|---|---|
| SEC-1 | XSS в комментарии решения: `<img src=x onerror=alert(1)>` | Отображается как текст, скрипт не выполняется, DOM не ломается |
| SEC-2 | Инъекции и мусор в `status`, `cursor`, `group_id`, `event_id` | `4xx`, без `500`, без текста ошибок БД и стека |
| SEC-3 | Огромные тело события, комментарий и `event_id` | Ограничение размера или `4xx/413`, процесс не падает и не ест память |
| SEC-4 | Админ-ручки без авторизации (`/admin-api/v1/scenarios/*/run`, `/notes/proxy`) | На prod закрыты сетью/Ingress или зафиксированы как риск MVP; любой желающий не должен запускать сценарии |
| SEC-5 | CORS, заголовки, ответы ошибок (ZAP baseline) | Нет `*` с credentials, нет stack trace, нет high-alert'ов baseline |
| SEC-6 | Много повторных запусков сценария и поток событий | Нет падения и неограниченного роста горутин/памяти; деградация контролируемая |
| SEC-7 | Секреты и PII в логах | Пароли, токены и полные payload'ы событий не пишутся в логи |
| SEC-8 | Зависимости и образы | Нет неразобранных critical/high: `govulncheck`, `pnpm audit`, Trivy |
