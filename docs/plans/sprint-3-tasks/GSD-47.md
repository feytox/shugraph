## Описание

Сборка групп в graph-api разбита на детекторы, по одному на схему, а в контракте группы есть признаки всех схем. После этой задачи адрес, цепочку и кольцо можно писать параллельно, а карточки этих схем во фронте делать на моках. Ферма переезжает на свой детектор, её поведение не меняется. Карточку во фронте на `features` переводит T-14.

## Проблема

Сборка сейчас написана под ферму и идёт под одной глобальной блокировкой, а каждое событие замораживает группы всех схем. Новые схемы пришлось бы вписывать в тот же код, и они ждали бы друг друга. Карточке нужны сами количества (клиентов, переводов, кругов), а в ответе есть только баллы за них.

## Решение

- [ ] Детектор схемы - общий интерфейс в graph-api: по событию создаёт или дополняет группы своей схемы и считает их риск. Приём события вызывает детекторы всех схем
- [ ] У каждого детектора своя advisory-блокировка и своя заморозка групп (SRD-9): детектор одной схемы не ждёт другой и не замораживает её группы
- [ ] Ферма работает через свой детектор, её интеграционные тесты проходят без изменений
- [ ] В контракте группы есть `features.<scheme>` для всех схем, по образцу `risk_parts.<scheme>`, с числами из `docs/cards/`: ферма - `clients_count`; адрес - `clients_count`, `devices_count`, `burst_minutes`; цепочка - `hops_count`, `preserved_percent`; кольцо - `rounds_count`, `preserved_percent`
- [ ] `features.farm.clients_count` хранится вместе с `risk_parts` и обновляется вместе с риском, а не считается при чтении. Признаки остальных схем заполнят задачи этих схем
- [ ] `docs/cards/`, `docs/entities.md` и `docs/definitions.md` описывают признаки как хранимые поля группы и ответа

## Тест-кейсы

1. Сценарий `device_farm`: та же группа, что до задачи, и `features.farm.clients_count = 3`.
2. В группу фермы приходит вход четвёртого клиента с того же устройства: `features.farm.clients_count = 4`, `risk_parts.farm.clients = 5`.
