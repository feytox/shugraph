# infra

Инфраструктура в Яндекс Облаке. Каждая часть в своей подпапке со своим README. Решения и альтернативы: `docs/rfc/01-zeroth-rfc/ci.md`.

## Яндекс Облако

- Если SSH к запущенной ВМ отваливается по таймауту отовсюду (из CI, локально, без VPN), это потери трафика в сети YC, а не наши настройки: помогает перезапуск ВМ workflow `down`, затем `up`.
- Во время сбоев yc падает с `Service is overloaded` или `poll fail ... Unavailable`, хотя операция могла пройти: проверять `yc operation get <id>` и состояние ресурса, а не код возврата.
- Квоты на зону: 2 vCPU, 20 ГБ HDD, 10 ГБ SSD, в ru-central1-b нули, поднять нельзя. Диск ВМ занимает весь HDD зоны, vCPU выключенная ВМ не держит.
- Пустая группа безопасности режет весь трафик, включая исходящий.
- yc: у правила с `protocol=any` обязателен `port=any`; в `--network-interface` группы только через `security-group-ids`.
- Сервисный аккаунт CI `shugraph-ci` имеет только `compute.operator` на ВМ и `container-registry.images.pusher` на реестре `shugraph`: к ВМ обращаться по `--id`, не по имени; новым действиям из CI нужны новые роли.
- YCR не принимает образы с provenance-аттестацией buildx: при сборке нужен `provenance: false`.

## Кластер

- 6443 снаружи закрыт: kubectl через `ssh shugraph@<ip> sudo k3s kubectl` или с kubeconfig ВМ (`/etc/rancher/k3s/k3s.yaml`) через `ssh -L 6443:127.0.0.1:6443`. IP меняется при каждом запуске ВМ.
- Настройки кластера и ВМ живут в файлах репозитория (манифесты, скрипты): вручную на ВМ применяем только для проверки, затем переносим в файл.
